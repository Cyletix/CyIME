## 审计口径

不能给出“整个应用还剩多少 bug”的可靠总数。本轮沿按键、引擎锁、输入会话、候选刷新和候选测量追踪，确认并处理 **8 个正确性/生命周期问题、3 个性能问题**。代码静态模式数量不是缺陷数量，也不能靠减少 catch 或重命名方法证明质量提升。

| 编号 | 已确认问题 | 本轮处理 |
|---|---|---|
| C1 | 九键处理/flush 与结果查询分开加锁；后一次 tryLock 失败可伪造空结果，选拼音/右选同样拆成多个操作 | 同一事务返回状态；退格同时返回操作前组合态和撤销段数 |
| C2 | reset/clearAll 排队后仍调用非阻塞 clear，锁忙时清空被丢弃 | 队列内等待锁完成清空 |
| C3 | UI 代际号由 Main 和后台共同自增；reset 后在途任务还能发布新的代际号 | 原子代际号，并给排队任务保存独立的输入 epoch |
| C4 | 准入票据只在部署时失效；切换输入框和销毁服务不作废旧任务 | 编辑会话更新票据；服务关闭不可被迟到启动回调重新打开 |
| C5 | T9 控制器的独立 CoroutineScope/Handler 不随键盘销毁结束 | DisposableEffect 调用 close，取消队列、清理回调并拒绝迟到发布 |
| C6 | 长按退格共用一组计数和首次回调，旧编辑会话能吃掉新会话重复请求；drain 吞掉 Throwable | 每组退格明确持有 admission/epoch/callback，旧批次只结束自己；删除吞异常循环 |
| C7 | 通用 updateUI 在主线程读 JNI，锁忙的默认空 composition 会清空真实候选 | 后台读取真实快照，回到 Main 前核验编辑会话及引擎版本 |
| C8 | setOption 直接调用 native，没有引擎锁 | 调用方在后台等待同一把锁；变更同步更新候选版本 |
| P1 | 展开候选在 Main 一次查询最多 500 项 | 后台每批最多 64 项，批间归还输入线程；null 明确表示过期，空列表表示有效快照已读完；追加不重置滚动 |
| P2 | 横排只显示一屏，却测量全部候选及注释 | 测量可见前缀及一个溢出项，剩余候选零文本测量；保留同一显示规则 |
| P3 | 自定义布局每键 flatten 全部字母并检测合并键 | 不可变布局实例缓存合并分组，修改布局生成新实例重新计算 |

## 语义与架构

- `engineRevision` 专门标识候选所属的引擎状态。显示文字、原始编码和候选身份不能混用；本轮没有假装已经迁移全部旧 `inputText` 使用者。
- 输入命令在后台队列执行，按键/flush/快照属于一个引擎事务。Main 只发布已校验的数据和操作编辑器。
- 展开候选复用现有输入工作线程分批读取，保留全局索引。公平引擎锁让等候中的输入有机会在批间执行。
- 不移除用户文件、插件、模型 I/O 的必要边界处理；内部不变量失败不能伪装为正常空输入。

## 仍需继续审计的已知风险

- 旧 Rime 查询/非队列 API 仍存在忙时 false/空值，包括工具面板部分操作。本轮迁移普通九键和通用刷新，不能宣称整个引擎已统一为单一命令入口。
- OnnxAssociationEngine.release 在同步入口 runBlocking 等待 Binder 卸载；InferenceClient.unloadModel 吞 Exception。要连同模型所有权、并发重载和解绑顺序一起改，不能简单 fire-and-forget，避免旧卸载杀掉刚加载的新模型。
- 联想层多处广义 Exception 捕获需要逐条区分 CancellationException 与可恢复 I/O；本轮没有批量删除异常处理。
- 候选点击与新输入交错时，全键盘全局索引的选择事务仍值得单独核对；本轮解决异步读取过期，不等于验证所有复杂选词序列。
- 需要物理手机/平板的帧时间与长句持续输入测量；控制器耗时不能代表屏幕呈现延迟，更不能直接宣称超过三星/Gboard。

## 验证和性能数据

优化前使用已保存的 1.1.8 修复 Debug（与 1.2.8 本轮输入代码基线相同）在 Android 36 x86_64 模拟器采样固定公开编码，不上屏、不训练用户词库。首轮预热后统计：

| 项目 | 样本数 | 中位数 ms | P95 ms |
|---|---:|---:|---:|
| T9 控制器到 Main 回调 | 160 | 3.62 | 9.11 |
| 全拼按键与快照 | 155 | 4.75 | 12.94 |
| 旧版一次查询 500 个展开候选 | 30 | 5.72 | 17.70 |

P95 采用 nearest-rank（排序后第 ceil(0.95×N) 项）。最终新版在同一模拟器、同一 Debug/测试路径独立采样（optimized129isolated）：

| 项目 | 样本数 | 中位数 ms | P95 ms |
|---|---:|---:|---:|
| T9 控制器到 Main 回调 | 160 | 4.03 | 10.38 |
| 全拼按键与快照 | 155 | 4.41 | 13.28 |
| 旧 API 一次查询 500 个候选（保留作对照） | 30 | 5.89 | 24.33 |

这组采样**不能证明九键端到端加速**。T9 中位数/P95 没有改善，全拼中位数略低但 P95 没有改善；不能据此声称整个输入流水线提速。一次查询 500 个候选的算法本身没有加速，新 UI 的收益是把它从 Main 移出、限制每次持锁批量，让排队输入能在批间执行。样本来自模拟器，单次前后采样有调度噪声，不代表物理设备帧延迟。

为避免选择性报告，保留前两次数据：最后一个普通按键 JNI 查询优化之前，T9/全拼中位数为 3.84/3.97ms、P95 为 10.24/12.08ms；最终版紧接事务回归采样时中位数为 4.28/5.18ms、P95 为 27.70/25.26ms。随后独立运行得到上表。最后优化仅让普通九键不再查询只对退格有用的操作前状态，减少两个不必要 JNI 查询；现有样本没有证明该微小改动带来稳定耗时收益。混合回归后的长尾不能隐藏，也不能用独立复测证明真实手机不会卡顿。

另用相同 Compose TextMeasurer、文本、字体和 620px 可用宽度交替测量旧算法与新算法（关闭测量缓存；每组预热 4 次后采样 20 次）：

| 总候选数 | 实际可见 | 旧/新测量项数 | 旧/新中位数 ms | 旧/新 P95 ms |
|---|---:|---:|---:|---:|
| 20 | 5 | 20 / 6 | 22.19 / 6.96 | 31.06 / 12.46 |
| 50 | 5 | 50 / 6 | 35.85 / 4.15 | 50.38 / 8.26 |

这是候选测量微基准，中位耗时分别约下降 69% / 88%，两种算法的可见项数断言一致。实际 UI 有缓存、字体/注释和布局开销，不能把这些比例套用为整体打字提速。
