# 按键到候选画出的分段耗时（2026-10-23，平板）

目的：量清从手指松开到候选这一帧画完，每一段各花多久，决定先优化哪段。本轮只测量，不改任何输入逻辑。

## 计时方法

- 代码：`app/src/main/java/com/kingzcheung/xime/service/KeyLatencyProbe.kt`，默认关闭，`adb shell setprop log.tag.CyIMELatency DEBUG` 后重新点进输入框才打开，关闭时每个打点只读一个布尔值。日志只有阶段耗时、布局、编码长度，不记按键和文字。
- 起点是触摸事件的系统时间戳（字母和九键都在松开时触发）；终点是包含这次结果的那一帧 HWUI 完成（FrameMetrics）。快速连打时多个按键同时在途，一次主线程应用覆盖它之前投递的按键，它们以同一帧为终点。
- 阶段：触摸送达（事件时间→键盘容器收到）、主线程处理（→进输入队列）、排队、后台（含引擎锁时间，单列“其中引擎”）、回主线程、应用（写候选状态）、等下一帧、重组（帧开始→键盘根组合应用）、布局绘制（→绘制开始）、渲染（→帧完成）。
- 终点之后到屏幕真正亮出来不在总计里：同一轮 `dumpsys gfxinfo framestats` 里帧完成到 DisplayPresentTime 中位 15 ms、p95 20 ms（120 Hz 下约两个刷新周期）。
- 汇总：`python tools/ime_lab/key_latency_report.py <logcat>`；驱动：`python tools/ime_lab/key_latency_drive.py`（单个 monkey 脚本，DispatchPointer 带非零按下时间、UserWait 控节奏，词间删除键下滑清空）。平板 shell 不能写 `/dev/input`，`adb shell input tap` 每次约 250 ms，都不适合快速连打。

## 条件

- 平板 SM-X800（Android 14，120 Hz），1.14.106（含 597fa0fb），宿主为系统设置搜索框（组字期间宿主不搜索）。
- 中文拼音 26 键与九键，同一组 13 个词／句（2～33 键），每档 4 轮共 644 键；节奏 100/60/35/20 ms 设定，实测按键间隔中位 107/66/40/25 ms，按住 25/20/15/10 ms。
- 注入事件从 InputDispatcher 开始，不含触摸屏扫描本身的延迟；也没测删除、选候选和打一半去点别处等情况。
- 原始日志：`D:/CyIME-Data/diagnostics/key-latency-20261023/`。全部 5152 键都有终点帧，没有丢失；结束画面均已清空。

## 结论

1. 正常速度（约 10 键/秒以下）每键 30～40 ms，其中界面固定花费约一半：重组 5～8、渲染 7～11，再加等下一帧 2～4；26 键引擎中位只有 6～12。
2. 九键长输入的最慢一成卡在引擎：8 键以上引擎 p95 50～72 ms，总计 p95 76～98 ms；26 键长句引擎 p95 21～31 ms。
3. 打得越快主线程越堵：40 ms 一键起“触摸送达”和“回主线程”两段都等主线程，25 ms 一键时短输入 p50 58～60、p95 88～92 ms。快速输入期间键盘几乎每帧都在画（60 ms 一键的一轮里 161 键画了约 1700 帧，26% 超过 120 Hz 期限），主线程被每帧的重组和绘制占满。
4. 每个词的头几个键渲染和布局 p95 偏高（11～22 ms），对应候选栏从无到有的那一帧。

## 先优化哪段

先优化主线程上每帧的重组和绘制：它出现在每一个键上，也是快速连打变慢的直接原因（触摸送达和回主线程都在等它）。已知线索是输入法根组合直接读整个候选状态，候选每变一次整棵键盘都要重组，以及打字期间按键动效让键盘持续每帧重画，这两点都需要先验证再改。其次是九键长输入的引擎尾部，用本地九键回放和速度门禁单独处理。
