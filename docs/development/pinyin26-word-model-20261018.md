# 26 键接上九键词组模型（2026-10-18）

用户放手由 Agent 定下一步。先做“26 键也用九键的词组模型排序”，再考虑口语语料重算雾凇词频。

## 做法

九键的联合解码器（`cmake/T9JointDecoder.inc`）由方案配置 `t9/joint_decoder` 打开，并不限于数字输入。构建时给 26 键方案（rime_ice，以及共用其配置的 QWJRTK、Cyletix10）加同一段 `t9:` 配置，使用同一个 `t9_ngram.lm`：

- `spelling_penalty: 0`：九键的 5 是给“一个数字键对应多个字母”的；26 键的字母就是声母本身，只打首字母不该再扣分。
- `correction_penalty: -9.2`（新配置项，默认 ln 0.01）：联合解码用词组模型打分，会把邻键纠错得到的词当成原样打出的词，所以纠错词每个扣分。九键没有纠错器，不受影响。
- `dictionary_beam: 64`（九键 16）：全首字母输入时每个字母展开几十个音节，16 会把“不知道”这类整词挤出束（bzd 曾出“不准动”）。
- `joint_requires_ngram: true`（新配置项）：手机上没有词组模型文件时，26 键回到原来的 Rime 词组/造句，不改用“词频＋语法＋每词扣分”。

以上三个数值只在自己的夹具与语料首字母集上选（日常短句、聊天、corpus-initials），公开测试集只用来下结论。

## 第二轮（同日）：保住用户报过的例子

第一轮后 zdky、hzp、zdh、hyddj 退步。逐条查到三个原因，都按原因修，没有给具体词加分：

1. **整词被搜索范围漏掉**：联合解码的词典束按“前缀单字权重”排序，hzp 的“化妆品”因“妆”字权重低，在第二个字母就被剪掉，模型根本没见到它。新增 `t9/whole_input_phrases: 16`：把覆盖整串的词典词（不经束搜索的精确查询，取前 16 个）直接放进候选。
2. **纠错单字插队**：10-17 的“原拼写整词排在纠错词前”只写在普通路径里，联合解码在它之前就返回了，于是“中”“这”这类纠错单字排到第 2。把这段提前到联合解码之前。
3. **26 键学习完全不生效**（选了也不往前排），两处：
   - 用户词库查找：开邻键纠错时，同一音节先列出的纠错边会让后面的原拼写简拼被跳过（`UserDictionary::DfsLookup` 的“只查一个简拼”规则），四字简拼 zdky 学过的“这都可以”查不出来。改为纠错边不占这个名额（不开纠错时与原规则完全一样）。这个问题在不接模型的 26 键也存在。
   - 联合解码合并候选时，学过的词和系统同名词按权重去重，留下系统词，用户层从未生效；且用户词权重刻度不同，会被候选池上限裁掉。新增 `t9/prefer_user_entries`：同名时留用户词，用户词不受池上限。26 键 `ngram_user_weight` 设 0.3（九键 0.05 不变）。

电脑上验证：zdky 选一次“这都可以”后即排第一；zdh 选两次“自动化”后排第一。九键配置未开这三项，行为不变。

## 1.14.10 崩溃与修复（1.14.11）

平板上 1.14.10 在 26 键中文按第一个字母即崩（SIGSEGV，栈顶 `ScriptTranslation::PrepareJointCandidates`）。原因：第二轮新增的“同名时留用户词”在 `std::remove_if` 的判断函数里又遍历同一个列表，`remove_if` 移动元素期间读到了被移走的空指针。电脑测试用的都是空用户词库，碰不到；平板有学过的词就必崩。电脑上复现：先上屏几个词，再打 n 即访问冲突。修复：先把学过的词（字＋编码）拷出来再删同名系统词。

新增 `tools/ime_lab/joint_learning_probe.py`：空用户词库下打 a–z 单字母和几个双字母；上屏几个词后再打一遍；zdky 选一次“这都可以”、zdh 选两次“自动化”后检查首选。修复后的电脑引擎通过（模型 v3 与私人 p4 各跑一次）。1.14.11 / 20261196 已打包（未安装）。九键配置未开该选项，不走这段代码；Windows 端没有联合解码器，不受影响。

## 各列不变差的开法与剩下的速度差（2026-10-20）

开法（电脑探针，`lexicon_regression.py --t9-set ...`）：`joint_decoder: true`，加三项——只打首字母时照旧走 Rime 原路径（`joint_skip_initials`），前文未知时不按句首打分（26 键从不传前文，`ngram_sentence_start: false`），四个音节以上才用词组模型（`joint_min_syllables: 4`，按输入里的元音段计），再加少见读音扣分（`reading_table`）。对 1.14.57 的词库：所有列不变差；整句首选 调参 LCCC 374→487、SMS 406→483，公开 LCCC 348→431、SMS 356→403、日常 149→161，14 类句式 1302→1338。`cache_with_correction: true` 打开后结果逐条相同。

速度：电脑逐键 p95 0.62→0.88 ms（14,643 键，三轮交替）。此前测到的“慢 7 倍”是 Windows 探针引擎里残留的 `getenv("CYIME_JOINT_DEBUG")` 在每次打分时都调用，仓库代码里没有。另把近键纠错判断从“每条路径×每个词”改为“每条边算一次”（探针里带 getenv 时 beam 段 8.8→6.8 s；去掉 getenv 后单独的效果未测，此改动只在探针里）。

剩下的差距在查词：每次解码平均重新查询 6.5 个起点、只复用 0.6 个（1,998 次解码共查 13,029 个起点，约 57 µs 一个），因为 26 键每多打一个字母，前面起点那一行就多出到新末尾的边，按“整行相同才复用”的规则全部判脏。Rime 原路径只查新桶（`LookupAll` 的 `min_end_pos`），所以快。要回到基线，需要让联合解码也只查“末尾超过上次长度”的新桶并与旧桶合并，并保证结果逐条不变：上次末尾处的补全（predictive）词条要丢弃，上次末尾以内的行（含纠错标记、可信度）必须相同，用户词典查询同样只补新桶。此项未做，用户也尚未决定是否接受 +40%，因此 26 键词组模型仍关闭。

### 增量查词试验（同日，未采用）

在电脑探针里给联合解码加了“只查新桶”：上次输入末尾之前的行（只看末尾之前的边）没变的起点，复用上次末尾之前的桶，只对末尾及之后用 `LookupAll(min_end_pos)` 补查；为不丢四字以上长词，另给 `LookupAll` 加了“保留所有起点、所有长词尾巴都收集再按末尾过滤”的精确模式。结果：每次解码 5.5 个起点走补查、只有约 1 个整查，但查词时间几乎不变（749→623 ms／1,998 次），连不精确的原启发式也一样，逐键 p95 仍为 0.86–0.88 ms。原因是表查询每次都要从起点把纠错扩展后的音节图整段走一遍，`min_end_pos` 只少收集、不少遍历。关掉近键纠错时两边是 0.24 对 0.39 ms，联合解码本身就比 Rime 原组句贵约 1.5 倍，查词之外的打分（语言模型）也占一半。

所以“查词增量”到不了基线。下一步可考虑的方向：不做全图联合解码，而是让 Rime 原路径照常出整句（快），只用词组模型给它的前几条整句和候选重新打分；或者把联合解码挪到停顿时异步算。两者都需要重新测选词效果。补丁留在 `D:/CyIME-Data/tmp/append_patch.py`、`tail_patch.py`。

## 改为“重新打分”并开启（2026-10-20，用户同意 +5%）
