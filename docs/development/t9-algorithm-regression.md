# 九键算法固定回归流程

日常选词测试直接在电脑运行当前仓库的 Rime、九键解码、候选排序与神经重排代码，使用现有词库、语法模型和句子模型。Windows 通过本机 WSL 执行 Linux 原生引擎；不连接平板，不依赖安装包，不运行 Android 界面，不打包或安装应用。

## 固定入口

从仓库根目录运行原聊天语料：

```powershell
python tools/ime_lab/t9_replay.py run --output .codex-artifacts/t9-host-current
```

首次运行在独立缓存内准备电脑端编译依赖及引擎；后续按源码指纹复用构建。当前机器默认 WSL 为 `Ubuntu-22.04-D`，其他 Linux 发行版可用 `--wsl-distro` 指定。Linux 上可直接用 Python 运行相同入口。需有现成 `org.json` JAR（默认查 Gradle 缓存，也可用 `--json-jar` 指定）。所有结果目录必须是新目录，防止覆盖旧证据。

每次保存原始输入、拼音、每个数字按键的候选、每个汉字读音完成时的首选、停顿后的候选和整句结果。`index.html` 为概览，`characters.csv` 为逐字明细，`report/index.html` 可检查全部按键和候选；`run.json`、`engine-build.json`、`resources.json` 保存来源和哈希，`quality.json` 保存约束结果。

对比修改前后的本机结果：

```powershell
python tools/ime_lab/t9_replay.py run --output .codex-artifacts/t9-host-after --baseline .codex-artifacts/t9-host-before
# 已有两份结果时无需重新运行引擎
python tools/ime_lab/t9_replay.py compare .codex-artifacts/t9-host-before .codex-artifacts/t9-host-after --output .codex-artifacts/t9-host-comparison
```

比较时重新核验原始数据和哈希，不信任预先生成的统计。语料、按键协议、初始个人学习状态必须一致；允许引擎、词库和模型改变，以测量改动结果。主机和 Android 的运行协议不同，不自动当作同一环境比较；跨平台候选一致性不能由本机回归通过直接推出。

## 给定新文本

准备 UTF-8 原文 `chat.txt` 和拼音 `chat.pinyin.txt`：后一文件按原文顺序给每个汉字一个完整拼音，用空格或换行分隔。标点、数字和英文保存在原文中，用来划分中文连续输入段，不送入九键中文引擎。例如：

```text
原文：你好，睡不着。
拼音：ni hao shui bu zhao
```

```powershell
python tools/ime_lab/t9_replay.py prepare --text chat.txt --pinyin chat.pinyin.txt --output chat.fixture.json
python tools/ime_lab/t9_replay.py run --fixture chat.fixture.json --output .codex-artifacts/t9-chat-new
```

支持带调字母、数字声调、ü/v 等规范化，并检查汉字数、拼音合法性、数字编码、原文位置和完整覆盖。`--auto-pinyin` 可使用已经安装的 pypinyin 生成读音，但会标记“未审阅”；多音字须核对，不能把错误读音算作输入法问题。原聊天夹具已经固定逐字读音，包括“睡不着”的 `zhao`。`--readings` 可提供按用例 ID 的完整读音纠正。

## 判定规则

- **直出**：当前汉字的完整拼音已经输入，首选与原文到该字的完整前缀相等。分别统计即时结果、逐字停顿结果和整段完成结果。半个音节的首选保留审查，不计入直出率。
- **回归**：目标候选从首选、前五、前百掉出，或名次下降；逐条保留改善与退步，不用总分改善抵消某句退化。超时、不接受按键、引擎实际输入丢字都算执行问题。
- **语言异常**：选错原文不自动等于不正常语言。已审定的异常按语料哈希、用例、按键位置和阶段精确绑定为断言；此次聊天已经保存 33 个异常时点。旧异常重现仍返回失败，即使和基线相同。新出现或改变的首选进入待审清单，审定后加入对应断言。
- **退出码**：`0` 表示采样完整且未违反已声明约束，不表示全部原文首选正确或语言自然度全部合格；`1` 表示已知异常、回归、执行问题或速度门禁不合格；`2` 表示环境、输入或证据无效；`3` 表示未发现回归，但速度门禁未完成或无法判定（如没有计时会话、旧结果无计数），不算通过。

不能把测试语料或答案灌入词库、添加专门命中的权重，再称为算法通过。异常断言仅检查输出，不参与引擎选词。

## 速度门禁：工作量与耗时

电脑端引擎以 `-DCYIME_T9_WORK_COUNTERS=ON` 编译（只在主机构建中打开；安卓构建不定义该宏，计数语句为空，生成源码与 APK 不变）。每个按键行增加：

- `work`：按键与 flush 期间回放线程的计数，包括词库 `Lookup`/`LookupAll` 调用、起点与表查询、表遍历节点与边、四字以上尾码匹配步数、取得的条目块与条目、用户词库查找与遍历、合并前后条目、束搜索评估/淘汰/插入、语法 `Query` 与 `GramDb::Lookup`、整句先验、解码结果缓存命中与帧复用。计数只累加，不参与任何选择。
- `inspect_work`：读取候选期间的同类计数；`process_us`：微秒级按键耗时。

计数只在回放线程累加：`t9_sentence_scorer` 后台线程的工作不计入（当前协议不请求整句评分）；音节图构建和候选策略没有计数，只由耗时覆盖。`dict_buckets` 是 `QueryMulti` 返回的（表、起点）对数。

**工作量**对同一引擎、输入和词库状态是确定的，没有噪声余量：

- 每个代价计数按“按键 + 读取候选”合计，逐个按键事件与基线同一按键比较：任何一个按键增加即不合格，即使总量和分布不变；逐键分布的总量、p50、p95、p99、最大值和停顿等待阶段的工作量也都不许增加。只看总量会掩盖“平均降低、个别按键变重”。
- 每个增加了工作量的按键按用例逐条列为不合格项（`comparison.json` 中有逐键数值，`comparison.md` 逐用例汇总），不取平均。
- 基线自身的重复差异就是允许范围：重复运行必须逐键复现主运行的工作量（目前实测为 0 差异），否则不合格。`--work-tolerance-percent` 只在写明理由时放宽，且按每个按键计算。

**耗时**的波动主要是整次运行的偏移（机器负载、文件缓存），单次“基线与其重复”的差值不能区分噪声和退化，只能在同一计时会话内判定：

- 基线引擎至少 3 次（基线 + 2 个 `--noise-baseline`）、候选 1 次以上（推荐 3 次，`--candidate-repeat`），依次单独运行、交替进行，首尾都是基线引擎，如 B C B C B 或 B C C B C B；相邻两次间隔不超过 20 分钟、不重叠；同一主机、同一运行器。
- 回放根目录必须在 Linux 原生文件系统。入口现在把 `native-run` 先放在主机缓存（`replay-roots/`）里运行，结束后移入结果目录，并在 `run.json` 的 `replay_root` 记录文件系统；放在 `/mnt/d`（9p/drvfs）时“热键”主要测到的是文件读入。
- 每个指标（热键即每个过程除第一个用例外的按键；均值/p50/p95，两种过程）用各次运行的平均值比较：允许差 = t₀.₉₉(n+m−2)·s·√(1/n+1/m) + max(基线 1%, 0.005 ms)，s 为基线与候选各自组内运行间标准差的合并值（单侧 1% 两样本 t 界）。超出允许差为不合格；未超出但大于基线各次极差的列为“需复核”警告。逐键配对差作为证据报告，不单独判定。
- 这个带只能识别大于运行间噪声的变慢。本机（混合大小核、WSL2、使用中以 nice 19 回放）同一引擎各次平均约有 5% 波动，按此估计允许差约为：3 基线 + 1 候选 ≈ 41%，3 + 2 ≈ 22%，3 + 3 ≈ 16%，5 + 4 ≈ 11%（均含 1% 下限）。十几个百分点以内的耗时变化无法由耗时判定，靠逐键工作量门禁（无噪声）把关；需要更灵敏时增加交替次数，不缩窄公式。曾用的“基线与单次重复的差值”作噪声带、或仅用基线各次极差作带，都已证明会把同一引擎判为变慢，不能使用。
- `--noise-baseline` 必须与基线同一引擎（库、资源、构建清单、部署方案，忽略时间戳），`--candidate-repeat` 必须与候选同一引擎，每次都是不同的运行；否则比较无效（退出码 `2`）。
- 不满足会话条件时耗时只报告，`speed_gate` 为 `incomplete`，比较退出码 `3`。某个过程的解码全部命中解码缓存时（小夹具的停顿过程），该过程的耗时不测解码，不作判定。
- 计数语句本身让停顿过程每键约多 0.06 ms（+1.2%）；基线与候选都用带计数的电脑端引擎，这部分相互抵消。

修改引擎源码后，用 `--engine-from <基线结果目录>` 重放基线的引擎和资源（不重新编译、不改源码），与当前源码的候选交替运行：

```powershell
python tools/ime_lab/t9_replay.py run --engine-from <基线B1> --output <B2>   # 基线引擎
python tools/ime_lab/t9_replay.py run --output <C1>                          # 当前源码（候选）
# ……按 B1 C1 B2 C2 B3 依次运行后：
python tools/ime_lab/t9_replay.py compare <B1> <C1> --noise-baseline <B2> --noise-baseline <B3> --candidate-repeat <C2> --output <新目录>
```

- 两种词库场景都要过；选词改进不能抵消任何速度退化。旧结果没有计数时显示 `unavailable`（退出码 `3`）。
- 2026-10-09 冻结的结果（`.codex-artifacts/t9-gate-tooling-20261009/runs/`）可作质量和工作量基线，但其回放根目录在 `/mnt/d`、与以后的运行不在同一会话，不能作耗时基线；耗时须在比较当次的会话里重新运行基线引擎。

## 预置个人词库场景

```powershell
python tools/ime_lab/t9_replay.py run --user-dict tools/ime_lab/fixtures/user_dict_seed_20261009.userdb.txt --output <新目录>
```

运行器在部署后、创建会话前，用 librime 自身的恢复流程把快照合并进隔离目录的 `rime_ice` 个人词库，并核对恢复条数。`run.json` 记录 `user_state: preset_user_dict` 与快照哈希；比较工具只允许同一快照的结果互比，永不与空词库协议混合。回放仍不提交、不学习。快照由词库词频抽样生成，不含测试句，见 `tools/ime_lab/fixtures/user_dict_seed_20261009.README.md`。快照中 `c` 为负的条目是删除记录，不计入恢复条数。

种子只有 3000 条、使用记录多已衰减，真实重度用户可能有 1–10 万条，所以测到的预置词库开销是下限；种子与聊天语料自然重合了少数整句（如“你呢”“真的”“知道了”），在该场景比较质量时要记得这一点。

## 执行边界与复现

电脑端编译使用隔离源码快照，避免现有 CMake 的插件复制和补丁步骤改动正在开发的源码。原 JNI 和候选策略继续参与计算；平台日志适配只把 Android 日志改发到标准错误。ONNX 使用支持同一 API 的 Linux 原生库，不关闭模型、不退回普通拼音引擎冒充当前算法。

词库快照取自当前源码及已经生成的中文资源，不依赖 APK。缺少必要词库、语法模型或句子模型直接失败，不自动打包。每次使用新的个人数据目录，不导入手机个人词库、不提交候选、不产生学习。原始聊天按连续中文段回放，段间清空组合；此协议测试无上下文学习的连续拼音，不模拟用户中途选词或微信上屏。

两个标准过程均逐数字调用真实引擎：连续输入在段末等候重排，逐字停顿还在每个完整音节处等候重排。默认每键额外等待 35ms，最多等候重排 5 秒；保存实际耗时和模型状态。异步线程、硬件与运行负载会影响即时快照和耗时，因此固定输入不能承诺逐毫秒完全相同；稳定后的候选单独检查，电脑耗时不作为平板性能结论。

只有用户明确要求设备诊断时才使用 `android-run`。本地算法测试通过也不等于输入法界面、按键触摸或实际上屏通过，这些仍须标为“未验收”。本批仅增加测试流程，未修改选词算法。
