# 1.2.9 九键长输入性能修复

## 验收范围

用户反馈 12–15 个九键编码后变慢、约 30 个时删除严重滞后；对照三星支持 63 字符（含分词符）。本轮以 63 字符作为压力测试长度，不用缩短输入上限解决问题。保留输入命令顺序、逐字退格、已提交正文和用户词库契约。

## 定位与方案

- simpleperf 采样集中在 `Table::QueryMulti`、`TableQuery::Access/Walk` 和内存分配。三层索引查询节点却使用四个可增长向量，每个搜索分支复制、分配；改为固定长度数组，并对拼音图与字典的有效子节点求交。
- 第一阶段是等价优化：182 个候选快照与原包完全一致，仍不足以解决长串输入。
- 旧增量造句图存在语义差异：同一前缀在逐字输入与从长串删除回来时，182 个记录中有 70 个候选快照不同。索引三层不等于词条最多三个音节；增量起点窗口和尾索引收集条件会漏掉长词。仅缓存旧增量图虽更快，但会固化这种差异，已放弃该实现。
- 九键自动造句图采用按起点、结束位置、索引深度分组、宽度为 8 的有界假设搜索；完整词条的直接查找不受此宽度限制。数字串不再使用上述增量词图。普通全拼与日语仍走原查询方式。部分合成句子的排名会改变，因此同时验证常用完整词条的召回。
- 只缓存系统字典生成的确定性前缀词图，按字典、方案指纹和黑名单失效；用户词库每次重新查询，上文相关造句重新评分。缓存同时限定前缀数和图大小，避免长时间输入无限占用内存。
- 第二次采样及地址解析确认 Debug 的逐分支 `DLOG` 仍创建 `google::LogMessage`，格式化线程号、拼音和数值。在 `common.h` 默认短路该跟踪，`CYIME_RIME_VERBOSE_TRACE=ON` 可显式恢复。保留 CHECK/DCHECK、普通警告和错误日志。关闭跟踪前后的 504 个候选快照完全一致。

## 最终包测量

同一 x86_64 Android 模拟器、1.2.9 Debug，默认九键方案。每组均逐键输入到 63 字符，再逐次删除到空；分词组包含尾部分词符。单位 ms；P95 使用最近秩。

| 63 字符用例 | 输入 P95 / 最大 | 删除 P95 / 最大 |
|---|---:|---:|
| 连续 7 | 26.92 / 30.07 | 21.81 / 24.47 |
| 确定性乱序数字 | 29.02 / 35.00 | 18.47 / 22.37 |
| 拼音数字串 | 31.62 / 36.67 | 14.05 / 17.70 |
| 含分词符 | 18.00 / 20.33 | 10.41 / 12.39 |

生产控制器每 35ms 入队一键、共 63 键：按键至引擎执行完成中位数 18.16ms、P95 27.06ms、最大 29.15ms；每个前缀均精确对应输入，没有末尾积压。70ms 周期长按退格，63 字符用时 4.429s，逐次长度检查通过。Main 心跳最大间隔 60ms，不能据此宣称界面无掉帧。

旧包复现记录中单次删除最大约 2.1s。该轮 63 字符基线与本机原生构建并行，存在系统负载差异，故只用作故障复现，不计算严格加速倍数。此前 30 字符同包对照也已经复现数百毫秒删除延迟。

最终数据：`.codex-artifacts/t9-long-final8-63.json`、`t9-long-final8-63-candidates.json`、`t9-long-queue.json`。四组共 504 个候选快照，输入/删除共有的 248 个非空前缀逐项一致，覆盖缓存命中及淘汰后的重新计算。9 个常用词分别带/不带分词符的 18 组召回检查通过。
